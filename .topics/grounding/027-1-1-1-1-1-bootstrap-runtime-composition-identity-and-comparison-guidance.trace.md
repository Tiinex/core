# Bootstrap Runtime Composition Identity And Comparison Guidance

## Objective

Make every manufactured portable Tiinex bootstrap truthfully self-identifying enough for a human or LLM to compare an already-loaded runtime with a newly supplied bootstrap without re-reading byte-identical bootstrap/schema/companion material or inventing a global newer-than relation.

## Done Criteria

- Embedded bootstrap manifest records an exact bundle manufacture timestamp with an explicit boundary that timestamp order is not semantic succession authority.
- Bootstrap runtime composition keeps one exact digest that is independent of bundle timestamp and changes only when the manifest-declared runtime representation changes.
- Portable Tooling exposes `version` as a read-only common command from an extracted bootstrap.
- `version` human default projects the bundle timestamp, exact Core package identity, runtime composition digest, runtime size/count, Schema Pack source identity and schema/companion counts.
- `version --tree` projects the full human-readable schema/companion dependency tree.
- `version --json` projects a stable machine-readable receipt containing Core identity, bundle identity, composition identity, Schema Pack source identity, every bundled schema with Parent relation and exact source digest, and the companion mode/facets actually exposed by the loaded runtime.
- Source-checkout invocation without a surrounding bootstrap manifest remains truthful: it reports an unbundled/source-runtime state instead of inventing a build timestamp or bootstrap identity.
- Bootstrap-only Start/transport guidance recommends the optional `version --json` identity comparison before broad runtime/schema re-reading, while preserving `orient` as the first semantic package operation.
- Guidance explicitly states that equal composition identity permits reuse of already-read runtime/schema/companion understanding, while differing identity requires inspection and does not make build timestamp, package version, receipt order, or different SHA a global supersession claim.
- Existing Package V1 manufacture remains the only bootstrap carrier manufacture path; no second bootstrap/package renderer is introduced.
- Full Core tests, portable smoke, embedded bootstrap qualification, standalone bootstrap-carrier manufacture and cold version invocation qualify.

## Scope

Core portable bootstrap manifest/runtime identity projection, portable CLI version surface, Package V1 bootstrap Start/transport guidance, and focused/full regression tests.

## Dependencies

- Qualified Handoff 082 Core baseline and its embedded bootstrap/carrier manufacture path.
- Native Schema Pack/catalog generated by Task 027-1-1.
- Existing canonical Package V1 bootstrap-only manufacture and transport projection.

## Boundaries

- No global bootstrap revision counter or `Supersedes` graph is introduced.
- No claim that a later build timestamp is semantically newer.
- No claim that a larger Core version necessarily supersedes a forked/differently composed runtime.
- No network access, npm lookup, GitHub lookup, CI dependency or host-private state is required for comparison.
- No schema-builder, companion-inheritance redesign, external-pack implementation, Workspace Representation redesign, or Package V2 work is in scope.

## Acceptance Boundary

The result provides truthful local comparison facts and composition discovery only. Choosing which non-identical runtime is authoritative remains governed by the qualified Handoff/task/source context; `version` itself does not grant that authority.
