## Adversarial Regression Boundary

- Case 1 — Cached Role Only: exact carried Role presence leaves all delegation authority slots unresolved; no delegate is selected and no Task/Handoff/manufacture sequence is offered
- Case 2 — Explicit Forward Selection: explicit upstream-qualified delegate/capability authority plus qualified process, target, source and return projections yields `qualified-for-delegation-authoring` and exactly the canonical Task -> Handoff -> carrier operations
- Case 3 — Individually Missing Slot: removing one required authority, including return/reconciliation, blocks the whole delegation path with only the exact missing-slot blocker and no next operations
- Case 4 — Empty Qualified Markers: process/source objects marked explicit+qualified but lacking substantive facts/provenance do not satisfy delegation readiness
- Case 5 — General Route Independence: missing delegation authority does not downgrade an otherwise qualified selected Handoff route from `grounded-to-act`; delegation is a separate diagnostic/mechanical gate
- Case 6 — No Semantic CLI Injection: Core did not add a generic CLI JSON authority flag; semantic projections must already be independently qualified upstream rather than becoming authoritative merely because an operator passed JSON to Tooling

## Preservation And Fidelity

- Preservation State: accepted blank/minimal Workspace cache grounding, holder-binding authorization, participant/process/source authority separation, bounded-vs-complete carriage, machine-derived carrier allocation, collision protection and general `grounded-to-act` semantics remain preserved
- Known Losses: none identified in the delegated Core source surface; delegation readiness is additive and does not replace existing route/orchestration readiness
- Fidelity Notes: the implementation adds a mechanical composition/diagnostic gate only; it does not reinterpret semantic authority or create a new participant/delegate model
- Workspace Fidelity: Workspace purpose, writability and carriage never become target/source permission merely because they are available
- Role Fidelity: cached/carried Roles remain grounding-only unless a separate upstream semantic projection explicitly selects a delegate/capability
- Process Fidelity: process inventory or Role adjacency never becomes applicability; substantive explicit upstream-qualified process facts/provenance are required
- Source Fidelity: repository/workspace availability and implementation-source creation authority remain separate claims
- Return Fidelity: a Handoff endpoint/completion string from unrelated carriage does not automatically become delegation return/reconciliation authority; the delegation projection must itself be explicit and qualified

## Interpretation Limits

- Not Yet Used As: actual delegate selection, participant map, process applicability, target repository permission, source creation permission, Business/Docs semantic disposition, orchestration plan, publication, release or deployment authority
- Must Not Be Treated As: permission to prompt a fresh specialist chat, scan repositories, select a Role because it is cached, fabricate a work plan, or infer missing semantic authority from filenames, directories or Handoff endpoints
- Does Not Prove: which specialist should receive future work, which process applies, which repository may be mutated, or which reconciliation semantics Business should adopt
- Must Not Be Used To Claim: authority to mutate Business or Docs, bypass exact upstream semantic qualification, weaken selected-route grounding, or treat Tooling-projected next operations as semantic work-plan content
